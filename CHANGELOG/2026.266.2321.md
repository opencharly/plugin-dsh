# 2026.266.2321 — fix: authenticate the dsh web probes with the launch token

## Summary

Authenticate the two dsh web-UI probes with the launch token that `dsh web`
(>= dsh-web-app 0.1.5-rc.x, here `@deepseek-ai/dsh 0.1.7-rc.1`) now requires.
A tokenless `GET /` returns **401**, so both hard-coded tokenless `curl` probes
got the auth fence's 401 — the two failing checks in `opencharly/pod-dsh`'s
`check-dsh-pod` R10 bed. After this change the bed passes end-to-end (see R10).

Per-file change (`git diff --numstat origin/main...HEAD`, head `5649577`):

| File | +/- | What |
|---|---|---|
| `candy/plugin-dsh/webprobe.go` | +17/−0 | NEW: the single shared `dshWebTokenProbe(port)` fragment — reads the launch token from `$DSH_HOME/web-token`, hard-errors on a missing/empty token, and curls `http://127.0.0.1:<port>/?token=$T` in-box. Used by both call sites (R3). |
| `candy/plugin-dsh/verb.go` | +10/−6 | `verbWebRunning` uses `dshWebTokenProbe("3080")`. |
| `candy/plugin-dsh/control.go` | +7/−2 | `DshStatusCmd.Run` uses `dsh --version && { dshWebTokenProbe("3080"); } && echo 'web UI: HTTP 200 on 127.0.0.1:3080'`. |
| `candy/plugin-dsh/webprobe_test.go` | +35/−0 | NEW: in-tree coverage locking in the token-authenticated shape. |
| `candy/plugin-dsh/charly.yml` | +12/−5 | `dsh-cli-skill` prose: the `web-running` and `status` bullets + the candy description state the token semantics. |

Why: `dsh-web-app 0.1.5-rc.x` mints a random per-process launch token and prints
it in its `dsh web: http://127.0.0.1:3080/?token=...` readiness line; the dsh
candy's entrypoint captures it to `$DSH_HOME/web-token`. There is no flag or
config that disables authentication. The probes must authenticate with it. `curl
-f` accepts the token exchange's 303 (no `-L` needed).

**Relates to:** `opencharly/pod-dsh#3` (the relocated `check-dsh-pod` bed that
exercises these two probes).
